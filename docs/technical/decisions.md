# Decisions

One line per decision, newest last. A third-party dependency needs an entry here.

- 2026-11-10 — Monorepo like tries.care: Rust workspace (`crates/`), Bun workspaces (`apps/`, `packages/`), Biome, TypeScript 7, catalogs for versions.
- 2026-11-10 — MIT, written from scratch. Upstream (`srtla` AGPL-3.0, `belacoder` and `belaUI` GPL-3.0) is a behavioural reference only: no copied or translated code. Protocol facts (packet types, lengths, timeouts) are documented in `docs/technical/protocol/` and implemented from there.
- 2026-11-10 — Rust crates: no third-party crates by default. `unsafe` forbidden except in dedicated FFI crates.
- 2026-11-10 — Rust where bytes flow (bonding, encoder, bitrate), Bun + Effect where we orchestrate (agent, server). The agent ships as one executable (`bun build --compile --target=bun-linux-arm64`), so the OS image has no JS runtime to install. Supersedes the all-Rust + Dioxus option.
- 2026-11-10 — `packages/domain` holds the pure model shared by agent, server and web, in the tries.care style (bounded contexts: aggregates, value-objects, errors, use-cases).
- 2026-11-10 — Web UI: TanStack Router + React + Effect, one app for the box's panel and the server dashboard. React, TanStack and Vite are accepted dependencies for the UI only.
- 2026-11-10 — Rust ↔ agent contract: local Unix socket, JSON messages, schemas defined in `packages/domain`.
- 2026-11-10 — Talk to NetworkManager / ModemManager over D-Bus, not by parsing `nmcli` / `mmcli` output.

- 2026-11-10 — Target board: Radxa ROCK 5T only (RK3588). No Jetson or other boards.
- 2026-11-10 — Linux dev and e2e tests run in an OrbStack VM on macOS, and on Ubuntu in CI.
- 2026-11-10 — Crate names say what they do: `bonding-protocol`, `bitrate-control`, `link-emulator`; later `bonding-sender`, `bonding-receiver`, `encoder`.
- 2026-11-10 — Own transport protocol (`docs/technical/protocol/freewheel.md`), plus SRTLA compatibility as a mode and as the benchmark baseline (also opens the IRL streaming market: phone apps and other boxes speaking SRTLA).
- 2026-11-10 — Cryptography only from an audited crate; never implemented in-house. Accepted exception to the no-dependency rule.
- 2026-11-10 — SRTLA-specific code lives in one module (`bonding-protocol/src/srtla.rs`); everything else uses generic bonding names.
- 2026-11-10 — Own native mobile apps (Swift, Kotlin), embedding the Rust transport crates through a C ABI. No cross-platform UI framework.

- 2026-11-10 — AEAD (ChaCha20-Poly1305 vs AES-GCM) decided by a benchmark on the ROCK 5T in M3.
- 2026-11-10 — `link-emulator` replays public cellular traces (Mahimahi format) until our own traces exist (M3).
- 2026-11-10 — CDN fallback (WebSocket through a CDN) accepted as the last resort in censoring countries.
- 2026-11-10 — A public benchmark on real cellular traces is a first-class deliverable (and our selling point).
- 2026-11-10 — Encoder drives Rockchip MPP through our own FFI, not GStreamer `mpph265enc`.
- 2026-11-10 — Dual encoding: adaptive live + fixed high-quality recording.
- 2026-11-10 — Server is a production switcher (decode + re-encode), not a relay.
- 2026-11-10 — Audio sources: the camera's microphone (UAC over USB) and an external receiver such as DJI Mic plugged into the box (USB audio); selectable, both recorded.
- 2026-11-10 — Borrow ideas from MP-QUIC and MoQ, not their wire formats.

- 2026-11-10 — Recording backfill is optional and policy-driven (off, outages only, highlights, everything; per link type: cellular vs Wi-Fi). The recording is cut into numbered, checksummed segments; the server tracks which ones it holds and only missing segments are sent. Nothing is rebuilt from the live stream (different encode).
- 2026-11-10 — Outage behaviour on the server is a setting: outage scene (animations, bets, highlights), raw (a few seconds of the real cut, no frozen frame, then the reconnection moment), or mixed (raw for a few seconds, then the scene). No frozen "connection lost" frame: it reads as alarming. "What you missed" replays are optional and never shift the live.
- 2026-11-10 — Mobile app audio: phone microphone or an external microphone (e.g. DJI Mic receiver on USB-C, or Bluetooth).

- 2026-11-10 — Safe deletion of recordings on the box: a segment can be deleted only after the server confirms it is stored (written to disk, checksum verified). Manual or automatic deletion; upload progress visible from the phone.
- 2026-11-10 — Default policy: cellular for live; full-quality upload on Wi-Fi, or on cellular when the plan allows.
- 2026-11-10 — Data accounting per SIM, keyed by the SIM card (ICCID): bytes up/down and throughput, full history kept, user-set plan cap (e.g. 25 GB), alerts, and a user-set renewal date (operators do not expose it).
- 2026-11-10 — Mobile app (iOS first, Android too): two screens, box control and live control (HUD, scenes, highlights, "what you missed"). Chat on the phone can be switched off to save data. Every feature can be turned on or off; the interface stays simple. Microphone picker like iOS.
- 2026-11-10 — Synthetic traces generated from statistics of public traces, so the benchmark does not depend on third-party files.

- 2026-11-10 — Code style: one thing per file, explicit names with units, layered TypeScript as in tries.care (`docs/technical/code-style.md`).
- 2026-11-10 — Two kinds of documentation: `docs/technical/` for builders, `docs/guide/` in plain language for streamers who are not technical. English first, French next.
- 2026-11-10 — `alloc-counter` is the first crate allowed `unsafe` (a global allocator), never linked into the box.
- 2026-11-10 — One benchmark baseline per platform; the CI gate runs on native `ubuntu-24.04-arm`.
- 2026-11-10 — Upstream behaviour is studied in a Docker lab (`labs/srtla-capture/`, Debian, upstream built at the pinned commit) rather than a full VM: same ARM64 Linux under OrbStack, reproducible in CI. Inside, network namespaces (box, net, server) with `tc netem` per link and direction, and 35 scenarios, one file each, covering baseline, link quality, outages, real conditions, addressing, lifecycle, limits and abuse. Each has a characterisation test; the same scenarios will judge our receiver and sender. Captures stay in `.cache/`; only a 120-packet fixture is committed.
- 2026-11-10 — The SRTLA compatibility mode reproduces upstream as is, quirks included (4 s dead-link timeout, slow ramp after recovery, unflushed ACK batches). Improvements belong to our own transport (M1b), so interop stays exact.
- 2026-11-11 — Fuzzing without a third-party fuzzer: seeded tests (exhaustive short inputs, every type at boundary lengths, random mutations of valid packets) run in `cargo test`, deterministic and on stable. Coverage-guided `cargo-fuzz` (libFuzzer, nightly) can be added later if a decoder grows complex enough to need it.
- 2026-11-11 — Event loop for the bonding receiver and sender: one thread, std blocking UDP sockets, and `poll(2)` through our own `net-sys` crate, the second crate allowed `unsafe` (research 05). `recvmmsg`/`sendmmsg` or io_uring later, measured, behind the same wrapper. Closes the open "async runtime" question.
- 2026-11-11 — Each bonding crate keeps its SRTLA-specific code in one `srtla` module (`bonding-protocol`, `bonding-receiver`, later `bonding-sender`); refines the single-module entry above.
- 2026-11-11 — Interop is judged by the lab: `RECEIVER=freewheel` runs the 35 scenarios with our receiver in place of `srtla_rec` (same command line), and the same characterisation tests must pass on those captures. Same plan for the sender.
- 2026-11-11 — `net-sys` also wraps `setsockopt(SO_SNDBUF)` (upstream's 8 MB send buffer per link) and `signal(SIGHUP)` (belaUI reloads the sender's link list with it; std has neither). Still the only bonding crate with `unsafe`; one `SAFETY:` comment per call. The sender's link sockets are non-blocking, as upstream's: a full buffer is a failed send, which disables the link.
- 2026-11-22 — M1b step 4, deadline-aware retransmission (ACK ranges, duplicate window on the server, resend within 1.5 s on spare window only): not kept. CI, 3 runs (run 45048513790) against step 3: `trace-drive` 511 frames lost against 517, `real-ride` 63 against 61, `all-links-drop` 186 against 186, within run-to-run spread. The frames we lose are lost while the links carry less than the stream, where a resend on spare window has nowhere to go. Kept on branch `m1b-step-4`; next, adaptive FEC.
- 2026-11-22 — M1b step 4, adaptive FEC: not built. Diagnosis first (`packet_capture::LossCauses`, second table of `bench-transport`; the lab now marks every `netem` setting): on the step 3 CI captures (run 44262198730, 3 runs, medians), every frame our transport loses is lost while the links together carry less than the stream, or in the 2–5 s it takes to catch up after (`trace-drive` 433 + 89, `real-ride` 61 + 0, `all-links-drop` 182 + 4); none to isolated losses while capacity sufficed, a dead link or a queue. FEC repairs isolated losses only and would spend capacity that is missing exactly then. Next: step 5, cross-layer bitrate.
- 2026-11-22 — M1b step 5, the lab's adaptive encoder: our own Rust tool (`crates/h264-encoder`, binary `lab-encoder`, Emilien's choice) calling libx264 through a small C shim compiled by its `build.rs` (x264's parameter struct is too large and build-dependent to mirror in Rust). Third crate allowed `unsafe`, one `SAFETY:` comment per call. libx264 is GPL-2.0: lab and CI only, never linked into anything on the box, which encodes with Rockchip MPP. Without libx264 at build time a stub builds, so `cargo test --workspace` runs anywhere; CI installs `libx264-dev`.
- 2026-11-22 — Transport → encoder: `freewheel-sender` sends a capacity report every 100 ms (`bitrate_control::CapacityReport`: usable links' estimated rates, live data sent, sent to arrive after 250 ms, dropped at the box) as one JSON object per datagram to the Unix socket named by `FREEWHEEL_CAPACITY_SOCKET` (Emilien's choice, the Rust ↔ agent contract). `bitrate_control::Controller` judges 500 ms of reports: under pressure (1 % dropped, or 20 % queuing) down to 80 % of the measured capacity and by at least a fifth; calm for 2 s, up 15 % a step while the capacity fits more, else 5 % (probing). A window full is not pressure: the stream's bursts fill the windows of links with room to spare.
- 2026-11-22 — The lab's adaptive pipeline: ffmpeg makes raw frames, `lab-encoder` encodes them, and a last ffmpeg muxes them into MPEG-TS with the audio, which its own ffmpeg makes live into a FIFO. Both inputs are read by the wall clock and renumbered at their own rate (`setts`). Audio made inside the muxer runs on another clock: the muxer then sent the video in bursts (100–250 ms holes, ~3 a second, measured with tcpdump in the lab image), which SRT turns into late frames; with a separate live audio, the largest hole is 49 ms (63 ms for the fixed encoder).
- 2026-11-23 — The transport gate judges the intact video (bitrate of the frames that arrived with exactly the encoder's bytes), not the bytes delivered (Emilien's choice): those count damaged frames (`trace-drive`: the baseline delivers 1822 kbit/s, 1077 of it intact), and an encoder that lowers its bitrate to lose fewer frames delivers fewer bytes by design. The bytes delivered stay in the table, for information. Frames lost and the longest gap still gate too; a quality score over time (SSIM or VMAF) may come later.
- 2026-11-23 — Capacity probing (`freewheel-sender`): padding on the links' spare capacity, never more than 10 % of the estimated capacity on average, and only while the encoder is below its ceiling (Emilien's choice), up to what the ceiling needs. Runs of 150 ms at twice the known rate; a link back from a stall is probed at once at its former rate; the controller climbs straight to the measured capacity. Design in `protocol/freewheel.md`, "Cross-layer bitrate and capacity probing". The padding is the background class, which the recording upload (step 6) will fill with useful data.
- 2026-11-23 — During an outage of every link, the encoder keeps its bitrate instead of falling to its minimum (Emilien left it to what is best for the stream; decided on the lab): nothing measures the links while they are down, and they come back at the rate they had. One run of `all-links-drop`: 132 frames lost and a 4.1 s gap held, against 195 and 6.4 s at the minimum (baseline 209, 6.9 s). Under pressure right after a cut of some links, the controller no longer lowers a stream that fits what the others carry (the pressure is SRT's catch-up); on links that stay, it still does (the measured capacity lags a drop: `trace-drive`, 432 frames lost against 172). It climbs at once when links come back. A cut is judged on a window of its own, 300 ms from the first report showing it, on the last measure: the links that stay are probed up from what they carried (CI 45173685823, `real-ride`: 2.1 Mbit/s at the cut, 4.9 Mbit/s 300 ms later).
- 2026-11-23 — Recording upload, M1b step 6 (Emilien's choices, plan in `plans/m1b-step-6.md`): the lab records a file growing at 6 Mbit/s (2× the live ceiling), compared byte for byte with the server's copy; after the stream ends the links stay up as long as the scenario took, and the bench reports the time to 100 %; the upload takes only what the live class leaves (latency p99 and intact video no worse than step 5); resumed across link outages only, a restart of the box or the server is a later step. The recording can be switched on and off, and every number of the upload is a setting.
- 2026-11-23 — `lab-encoder` holds its bitrate by the VBV buffer (capped CRF) instead of x264's ABR, which took ~10 s to climb from 0.3 back to 3 Mbit/s; at a constant setting both give the baseline's bitrate, and the box's hardware encoder in constant bitrate follows a new one at once too.
- 2026-11-23 — Background payload (M1b step 6): a kind byte, then for padding zeros only (step 5's padding, 1 480 zero bytes, is already valid) and for a recording chunk its 64-bit offset in the recording then its bytes (1 – 1 471). An offset, not a chunk number, so a resend is idempotent and the chunk size stays a sender's setting. Decoded as strictly as the packets, with the same proofs; the packet layer keeps data payloads opaque, so a receiver without a recording behaves as before.
- 2026-11-23 — Recording upload on `trace-drive` (Emilien's choice): its links stay up 180 s after the stream (twice its length) instead of 90. Once the traces end they hold 3.96 Mbit/s (44.5 MB in 90 s), and during the stream they carry 55.3 MB of which the live takes ~25 MB in bursty seconds the upload must not queue: the 67.5 MB recording cannot arrive whole in 90 s (60 % in a lab run), and needs ~125 s. Still 6 Mbit/s, still gated at 100 %; the other scenarios keep a drain as long as their stream.
- 2026-11-24 — Recording upload while the live stream runs (Emilien's choice): on each link, the upload's bytes in flight stay under the live bytes in flight there (`FREEWHEEL_RECORDING_LIVE_RATIO_PERCENT`, default 100), with no cap once the live stream is idle (the drain). A link whose capacity drops at once delivers what it holds late, the live packets behind the upload's included: CI 45278362883, `varying-bandwidth` (8 → 1 Mbit/s), SRT resent what came late, the live traffic overflowed and the encoder backed off for 3 s twice (intact video 2922 kbit/s against step 5's 3046). On the simulated drop, live p99 80 ms without the upload, 347 ms uncapped, 160 ms at 100 %, 265 ms at 200 %; the upload carries 2.8, 6.3 and 5.4 Mbit/s during the stream, the rest goes in the drain.
- 2026-11-24 — Encryption, M1b step 7 (Emilien's choices, plan in `plans/m1b-step-7.md`): Noise `IK` through `snow` (audit checked and cited before the dependency goes in), so the box, which knows the server's static key, opens a session in one round trip carried by Join and Accept; ChaCha20-Poly1305 by default, AES-256-GCM as a setting until the M3 benchmark; the 12-byte header stays in clear, authenticated as associated data, everything after it encrypted; one static key pair per box, the server holding the list of authorised box keys (an unknown box is refused), keys resettable, every path and key a setting; a sliding replay window over the nonce per session and direction, rekeying later. Plaintext v0 stays behind an explicit setting (`FREEWHEEL_PLAINTEXT=1`), encryption on by default, so the bench measures its cost and plaintext is proved step 6 to the bit.
- 2026-11-24 — Encryption's crates (M1b step 7, plan `plans/m1b-step-7.md`): `snow` 0.10.0 for the Noise `IK` handshake, `chacha20poly1305` 0.10.1 and `aes-gcm` 0.10.3 for the transport, the versions `snow` itself builds with. Audits: `snow` was reviewed by Trail of Bits for 1Password in March 2024 (`trailofbits/publications`, `reviews/2024-03-agilebits-snow-securityreview.pdf`, announced by 1Password on 2026-06-16): 10 findings (1 medium, a nonce-handling flaw, 1 low, 8 informational), 8 fixed, the 2 left informational; 0.10.0 (July 2025) postdates the review, and RUSTSEC-2024-0011 was fixed in 0.9.5. Its README still says "not received any formal audit": it predates the review. `chacha20poly1305` and `aes-gcm` were reviewed by NCC Group for MobileCoin (report of 2020-02-12): no vulnerability found, constant-time techniques as recommended. `snow`'s X25519 is `curve25519-dalek` 4, BLAKE2s is `blake2` 0.10, randomness `getrandom`. Our transport does not go through `snow`'s: its `StatelessTransportState` takes an explicit nonce but no associated data, and the clear header must be authenticated. So `snow`'s `risky-raw-split` feature hands over the handshake's two keys, and `freewheel-noise` seals with the AEAD crates the way Noise's `CipherState` does (`EncryptWithAd`, nonce = 32 zero bits and the 64-bit counter, little-endian for ChaChaPoly, big-endian for AESGCM): no cryptography of our own. Everything that touches a key is in `crates/freewheel-noise`; `bonding-protocol` only frames (`Envelope`, `frame_sealed`).
- 2026-11-24 — Encryption's design, where the plan left it open (M1b step 7): the handshake has two kinds of its own in v1, hello (`0x07`, IK's first message) and welcome (`0x08`, its second), so a sealed join (a later link) and a hello never look alike. The prologue binds the session id, not the link id: the box sends the same hello on every open link, and retries it unchanged every 250 ms until a welcome comes; the server keeps that hello and its welcome per session, answers every copy with the same welcome (no new handshake, no second DH), and registers each link it came on. The hello's payload is its handshake number in the session (from 1): a hello whose number is not above the session's is a replay and dropped (Noise `IK`'s first message can be replayed; WireGuard uses a timestamp for the same reason). A box the server does not know, a forged hello, a sealed packet it cannot open: dropped unanswered and counted (`RejectedPackets`), never a clear `Close` the box could not authenticate anyway. So a box restarted against a live server, or a server restarted under a live box, has no clear refusal to go by: the box opens the session again (handshake number + 1) when nothing has opened for 3 s (`REHANDSHAKE_SILENCE_US`), and each side keeps the previous keys until a packet opens with the new ones, so what was in flight still opens. Replay window: 8192 packets per session and direction (500 ms at 196 Mbit/s of full datagrams), `FREEWHEEL_REPLAY_WINDOW_PACKETS` on the server. Residual risk: a copy of a session's current hello, replayed from another address with another link id, registers a link that carries nothing (no packet goes to a link before an authenticated one comes from it) until it times out (10 s).
